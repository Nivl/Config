# pr-review: stop posting AGENTS.md as the source of a finding

Date: 2026-08-03
Target file: `shared_config/.claude/skills/pr-review/SKILL.md` (one file)

## Goal

A posted review comment currently reads `AGENTS.md "Code comments" says: ...`. The rule is the
reviewer's own, from their global `~/.claude/AGENTS.md`, which is usually not in the repo under
review. A teammate reads the comment, opens the project's AGENTS.md, finds nothing, and concludes
the finding was invented. The finding itself is correct and wanted. Only the attribution changes.

## The two leaks

Two independent paths put the string into a posted comment. Both must close, and a fix to either
one alone leaves the confusion in place for some findings.

| # | Where | What leaks |
|---|---|---|
| 1 | The finding's own description, generated by `in-depth-review/SKILL.md:335` ("When flagging, cite the specific AGENTS.md file and the rule text") | `AGENTS.md "Code comments" says: ...`, in both global and inline comments, because `pr-review` passes `<description>` through verbatim |
| 2 | `pr-review/SKILL.md:805`, the global body template | `<description, including category and any suggested-fix alternatives>`, and for these findings the category IS `AGENTS.md` |

Leak 2 is also a pre-existing inconsistency. The inline template at `:896` already reads
`<description, including any suggested-fix alternatives>` with no category, so the two templates
disagree today.

## Why this is a pr-review change and not an in-depth-review change

The obvious fix is to stop Role #1 citing the file at source. That is the wrong layer, for two
reasons.

**The scorer needs the citation.** `in-depth-review`'s confidence rubric assigns 25 when, for an
AGENTS.md issue, "the cited rule doesn't actually call this out". That is an anti-fabrication check,
and removing the citation removes the scorer's ability to run it.

**`review-and-fix` is not affected by the problem.** It shares Role #1 but never writes to GitHub.
Its findings go to chat and to commit messages, read by the person who owns the AGENTS.md. There the
citation is useful rather than confusing. A source-layer fix would degrade that skill to solve a
problem it does not have.

So the citation stays internal and is rewritten at the posting boundary. `pr-review` already owns
that boundary and already states the doctrine, at `:773-775`: "The POSTED comment never shows the
number, the agreement count, or the source skill. Those are internal mechanics that confuse
readers." Rule attribution is another internal mechanic leaking. This change extends an existing
rule rather than inventing one.

## Decisions taken

| Decision | Choice | Why |
|---|---|---|
| Register of the replacement | An unattributed norm. State the rule with no source named. | Considered and rejected two alternatives. "Convention I apply on review" is honest but invites "whose convention, and why does it bind me", which reads as a personal nitpick on someone else's PR. A rationale-only version claims no authority at all, so it invites a fresh debate on every instance instead of settling the class once. |
| Generalization | The wording must carry non-style rules too | AGENTS.md also governs TypeScript casts, error handling, and logging levels. Any register containing the word "style" fails on "Style convention: narrow with a type guard rather than casting". The chosen register has no such word. |
| Keep the rule's permitted list | Yes | The list of what IS allowed (hyphenated words, CLI flags, ranges, label prefixes, ratios) is what tells the author where the boundary is. Dropping it turns the comment into a bare prohibition. |
| Which layer | `pr-review` only | See the section above. |
| Category label in the global body | Drop `including category` entirely | Closes leak 2 with no special-casing and makes the global template match the inline one. This is broader than the AGENTS.md case, so `bug` and `security` stop printing too. Accepted deliberately. The alternative, printing every category except `AGENTS.md`, needs a special case in a template and leaves the two templates inconsistent. |
| Layer at which titles are covered | Same rule covers title and description | A title can carry the attribution just as easily, for example "Violates AGENTS.md comment rule". |

## Change 1: the Rule attribution block

Insert into Step 3b, immediately after the confidence-label block and before the fenced global-body
template.

Anchor to find. It spans the end of the confidence block and the start of the global-body template,
which pins the position. Note that the anchor itself contains a triple-backtick fence, so the blocks
below are fenced with FOUR backticks to hold it:

````
those findings, and a `[<ticket_id>]` title prefix for ticket findings).

```markdown
I used an AI agent with a custom prompt to generate this review.
````

Insert the new block between that first line and the fence, giving:

````
those findings, and a `[<ticket_id>]` title prefix for ticket findings).

**Rule attribution (what the reader sees).** A finding may arrive citing the AGENTS.md file and
rule text it came from. Role #1 of `in-depth-review` is told to cite both, and that citation is
what lets the scorer check the rule says what the finding claims. It is internal mechanics, the
same as the confidence number. **Never post the file name, and never post a phrase like
"AGENTS.md says".** The reviewer's AGENTS.md is usually not in the repo under review, so a reader
goes looking for a rule that is not there and concludes the finding was invented.

State the rule directly instead, as a norm with no source attached, and keep whatever the rule
permits, since the permitted list is what tells the author where the boundary is:

> One thought per sentence, and don't glue two clauses with a colon or a dash. The colon after
> "DB I/O" splits a claim from its elaboration. Hyphenated words, CLI flags, ranges, label
> prefixes and ratios are fine, but this is not one of those.

This governs the title as well as the description, and inline comments as well as global ones.

Two ways to get this wrong. Do not swap the citation for a vaguer authority such as "the project
requires" or "the team convention is". That is worse than naming the file, because it asserts
something about this repo that is not true. And do not soften the rule into a preference, because
the finding still has to read as actionable rather than as one reviewer's taste.

```markdown
I used an AI agent with a custom prompt to generate this review.
````

The closing paragraph is load-bearing. Without it an agent drifts toward "I would prefer two
sentences here", which is the rationale-only register this design rejected.


## Worked example

The comment that prompted this change, before:

```
**New comment glues a claim to its elaboration with a colon** `[confidence: Critical]`

AGENTS.md "Code comments" says: "One thought per sentence. Don't glue clauses with a dash or a
colon." Its own Bad/Good example is this same shape. The colon after "DB I/O" splits a claim from
its elaboration, which is not one of the listed exceptions for hyphenated words, CLI flags, ranges,
leading label prefixes, ratios, or code and paths.
```

After:

```
**New comment glues a claim to its elaboration with a colon** `[confidence: Critical]`

One thought per sentence, and don't glue two clauses with a colon or a dash. The colon after
"DB I/O" splits a claim from its elaboration. Hyphenated words, CLI flags, ranges, leading label
prefixes, ratios, and code or paths are all fine, but this is not one of those.
```

Note what survived. The rule, the specific location, the reason, and the permitted list. Only the
sourcing and the "its own Bad/Good example" appeal to the document are gone.

## Known follow-ups from the reviews (parked, not applied)

Recorded here because the SDD workspace holding the review ledger has been deleted and these
rulings are not in git history. None is load-bearing. All were adjudicated rather than fixed,
since the process allows no second fix wave.

**R1. `pr-review/SKILL.md:930` says "strip the source file name", which is ambiguous here.** In a
code-review skill, "source file" reads first as the file under review rather than the file the rule
was sourced from. The opening clause "Step 3b's rule applies here unchanged" disambiguates it, so
this is mild. One-word fix if wanted: "strip the convention file name". It stays under 98 columns.

**R2. `pr-review/SKILL.md:808` still abbreviates the permitted list.** The worked example now
includes code and paths, but the rule it illustrates also permits "times" and "URLs". This is the
same defect the review's Finding 3 was meant to close, only partially closed, because the fix
specified the two missing items without checking the full source list. By the block's own standard
at `:802-803`, keep whatever the rule permits, the example still teaches abbreviation. One-line fix:
`> prefixes, ratios and times, and code, paths, or URLs are fine, but this is not one of those.`

**R3. Nothing carries the convention citation as a structured field.** It lives in free text inside
`description`, per `in-depth-review/SKILL.md:335`. So Step 3c.7's "a finding that arrived with a
convention-file citation" has to resolve against inbound prose after Step 3b already rewrote the
body. It is recoverable, because the pool still holds the original description, but there is no
field to key off. Related: `citation_verified` in the finding schema means commit and PR citations
from other roles, not convention citations, so two senses of "citation" now sit in adjacent steps.
If this ever gets fixed, a dedicated field would settle both.

**R4. Step 3b carries no forward reference to the Step 3c.7 carve-out.** An agent reading Step 3b
alone believes the ban is unconditional. That error runs in the SAFE direction, since it omits a
convenience line from a local file rather than leaking a filename to GitHub. Optional symmetry line
after `:810`: "The one place the citation is kept is the local approval file in Step 3c.7, which
never reaches GitHub."

**R5. The "internal mechanics, the same as the confidence number" analogy at `:794` is no longer
exact.** The confidence number appears nowhere, including the local approval file, while the
citation now does appear there. The analogy is used only to justify not posting, so it misdirects
nothing, but it is imprecise.

## Out of scope

- `in-depth-review`. Role #1 keeps citing the file and rule text. The scorer needs it.
- `review-and-fix`. It never posts to GitHub, so its findings keep the attribution, which is useful
  to the person who owns the AGENTS.md.
- `gh-style-review`'s own behaviour stays as it is. **Correction to an earlier draft of this spec,
  which claimed it "does not cite AGENTS.md".** That was wrong. It references `CLAUDE.md` eight
  times, including its own `CLAUDE.md` category value and a confidence anchor for "a provable
  convention / CLAUDE.md violation". So it is a SECOND upstream that can produce a doc-attributed
  finding, under a different filename. The final review caught this. The posting-boundary rule now
  names both files and both sub-skills, which is why no change to this skill is needed. Do not
  reintroduce the claim that it never cites a convention file.
- The `category` field itself, and the category-priority tiebreaker at `pr-review:445`. Both stay.
  Only the template line that PRINTS the category changes.
- Any change to which findings are posted. This design changes wording only, never the filter, the
  threshold, or the classification.
